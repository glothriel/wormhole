### Task 03: Serialize syncs with peer deletion in `syncing.Server`

**Goal:** Add `syncing.Server.DeletePeer`, which removes the peer record and then the peer's metadata and apps, never interleaved with handling a sync.

**Context:**
- Read first: `pkg/syncing/server.go`, `pkg/listeners/exposer.go`.
- Sync handling and peer deletion share one mutex. The mutex covers the handling of one sync from decoding to encoding the response; the response or error is sent to the transport after the mutex is released.
- `DeletePeer` runs the caller's record deletion under the mutex. If it fails, `DeletePeer` returns that error and does no cleanup.
- After the record is deleted: delete the metadata, then `RemovePeer` on the generator. A metadata deletion failure is logged and does not stop the withdrawal or change the return value.
- Withdraw failures are already logged by `Registry.Watch`, which still drops the app from the list.
- `DELETE` may return before the last app's exposer calls finish; that is accepted.
- `Registry.List` is not synchronized with `Watch`; tests read it only after stopping `Watch` through its `done` channel.

**Acceptance criteria:**
- [ ] After `DeletePeer`, the peer's metadata is gone and its apps are withdrawn; another peer's same-named app and metadata stay.
- [ ] A sync from the deleted peer is rejected as unknown.
- [ ] A failing record deletion returns its error and leaves metadata and apps in place.
- [ ] A failing `Withdraw` for one app or a failing metadata deletion is logged, and all the peer's apps are still withdrawn.
- [ ] A concurrent sync and deletion of the same peer never leave its apps or metadata behind, under `-race`.

**Changes:**
- `pkg/syncing/server.go` — add a mutex to `Server`, move the per-sync handling of `Start` into a method that holds it, and add:
  `func (s *Server) DeletePeer(peer string, deleteRecord func() error) error`
- `pkg/syncing/server_test.go` — new file, using a real `listeners.Registry` fed by the generator, with these cases:
  deleting p1 removes its apps and metadata and keeps p2's same-named app and metadata (AC1, AC3, AC8);
  a sync from p1 after deletion is rejected (R5);
  a failing record deletion returns the error and cleans up nothing (R8);
  a failing `Withdraw` for one app is logged and every app of the peer is still removed (AC6);
  a failing metadata deletion is logged and the apps are still removed (AC7);
  a sync and a deletion of p1 run concurrently 50 times, and p1 never ends with apps or metadata (AC5).

**Validation:** `go test -race ./pkg/syncing/...`
