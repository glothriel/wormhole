### Task 03: Clean up a peer's metadata and apps on `DELETE /api/peers/v1/:name`

**Goal:** After the peer record is deleted, delete the peer's metadata and withdraw its apps, serialized with sync handling so an in-flight sync cannot bring them back.

**Context:**
- Approach: `syncing.Server` owns the serialization. It gets a `lock sync.Mutex` held for the whole handling of one sync (decode, peer lookup, `metadata.Set`, `UpdateForPeer`, app list, encode). A new method `DeletePeer(peer string, deleteRecord func() error) error` takes the same lock, runs `deleteRecord` (the existing WireGuard + peer record removal in `PeerController.deletePeer`, `pkg/api/peers.go`, unchanged), and only if it succeeds calls `metadata.Delete(peer)` (task 01) and `stateGenerator.RemovePeer(peer)` (task 02).
- Rejected alternatives: routing deletions through the `Start` loop over a channel (same guarantees, more plumbing); sending withdraw events from a goroutine after unlocking (a peer re-pairing under the same name right away could get its fresh apps withdrawn).
- Consequence: withdraw events go over the existing unbuffered channel consumed by `listeners.Registry.Watch`, so DELETE returns once the Watch loop has taken the last event. The exposer calls (k8s, nginx) for the last app may still be running when 204 is sent. This latency is accepted; cleanup never changes the response.
- Rules:
  - DELETE responses stay as today: 204 on success; 500 when the peer is not found or the WireGuard update or `peers.DeleteByName` fails; 401/500 from `RequireBasicAuth` unchanged. On any `deleteRecord` error, no cleanup runs.
  - A failing `metadata.Delete` is logged with `logrus.Errorf("failed to delete metadata for peer %s: %v", peer, err)` and `DeletePeer` still withdraws the apps and returns `nil`.
  - A failing `Exposer.Withdraw` is already logged by `Registry.Watch` (`"Could not withdraw app: %v"`) and the app is still removed from the list. Do not change `pkg/listeners/exposer.go`.
  - `incomingSync.Response` / `incomingSync.Err` are sent after the lock is released.
- `pkg/syncing/server.go`: `Server.Start` ranges over `s.transport.Syncs()`; `ServerTransport` has `Syncs() <-chan IncomingSyncRequest` and `Metadata() map[string]string`; `IncomingSyncRequest{Request []byte; Response chan []byte; Err chan error}`. Messages are `syncing.Message{Peer, Metadata, Apps}` encoded by `NewJSONSyncingEncoder()`.
- `pkg/listeners/exposer.go`: `listeners.NewApps(exposer)` returns `*Registry`; `Registry.Watch(changes, done)` returns after receiving from `done`; `Registry.List()` returns the internal slice without locking. In tests, read `List()` only after `done <- true` has completed (the unbuffered send happens after Watch has finished processing every earlier event, which makes the read race-free). `listeners.NewNoOpExposer()` exists. `pkg/listeners` does not import `pkg/syncing`, so `pkg/syncing` tests can import it.
- `pairing.NewInMemoryPeerStorage()`; `PeerInfo{Name, IP, PublicKey}`; `GetByName` of a missing peer returns `pairing.ErrPeerDoesNotExist`.
- `wg.Config{Address, Subnet, ListenPort, PrivateKey, Peers}`; `wg.NewWatcher(path)` writes the rendered config to `path` on `Update`.
- Log assertions use `logtest "github.com/sirupsen/logrus/hooks/test"` (`logtest.NewGlobal()`, `hook.AllEntries()`), part of the existing logrus v1.9.3 dependency.
- `tests/test_kubernetes.py` e2e tests use the `kubectl`, `k8s_server`, `k8s_client`, `helm`, `curl`, `mock_server` fixtures, `Annotator`, `@retry(tries=DEFAULT_RETRY_TRIES, delay=DEFAULT_RETRY_DELAY)`, and `curl.call_with_network_policy([...], max_time_seconds=10)` against `http://wormhole-server-api.server:8082`. The client peer is named `client`. k8s resources created for remote apps carry the label `wormhole.glothriel.github.com/exposed-peer=<peer>`. `k8s_server` enables network policies. `test_peer_deletion` stays unchanged.

**Acceptance criteria:**
- [ ] `DELETE /api/peers/v1/<name>` of a peer that synced apps returns 204; afterwards the peer's metadata is gone and its apps are withdrawn from the registry; another peer's app with the same name and its metadata are untouched.
- [ ] A sync from the deleted peer is rejected with `pairing.ErrPeerDoesNotExist`.
- [ ] When `deleteRecord` fails, `DeletePeer` returns its error, metadata and apps stay.
- [ ] A failing `Withdraw` for one app is logged; all the peer's apps are gone from the registry.
- [ ] A failing `metadata.Delete` is logged; `DeletePeer` returns nil and the apps are withdrawn.
- [ ] A sync and a deletion of the same peer run concurrently 50 times under `-race`; every time the registry ends with no app of the peer and the metadata storage returns `ErrPeerNotFound`.
- [ ] API: no credentials → 401; unknown peer → 500; known peer → 204 and the peer is gone from peer storage.
- [ ] New e2e test shows the deleted peer's Services and NetworkPolicies disappear and `GET /api/apps/v1` has no entry for it.
- [ ] `uv run --project tests pytest -v --tb=short tests/test_kubernetes.py -k test_peer_deletion` passes (runs the new e2e test together with the unchanged `test_peer_deletion`; needs Docker and k3d, as in `.github/workflows/integration.yaml`).

- `pkg/syncing/server.go` — add:
  ```go
  // DeletePeer runs deleteRecord and, if it succeeds, removes the peer's metadata and withdraws
  // its apps. It never runs concurrently with handling a sync.
  func (s *Server) DeletePeer(peer string, deleteRecord func() error) error {
  	s.lock.Lock()
  	defer s.lock.Unlock()
  	if err := deleteRecord(); err != nil {
  		return err
  	}
  	if err := s.metadata.Delete(peer); err != nil {
  		logrus.Errorf("failed to delete metadata for peer %s: %v", peer, err)
  	}
  	s.stateGenerator.RemovePeer(peer)
  	return nil
  }
  ```
